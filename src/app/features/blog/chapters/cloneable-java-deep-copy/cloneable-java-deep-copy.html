Cloneable no Java: shallow copy, deep copy e por quê evitar

Por que a interface Cloneable é desencorajada por especialistas como Joshua Bloch e Brian Goetz, e o que usar no lugar dela.

Clonar um objeto em Java parece simples. Na prática, exige escolher entre shallow copy e deep copy, e a interface pensada pra isso, Cloneable, é considerada quebrada pelos próprios arquitetos da linguagem.

Duas abordagens

Shallow Copy (Cópia Rasa)

Apenas copia as referências dos objetos internos, sem criar novas instâncias.

Problema:

  • Objetos internos continuam compartilhados entre a cópia e o original.
  • Qualquer modificação pode afetar ambos, resultando em efeitos colaterais inesperados.

Deep Copy (Cópia Profunda)

Cria novas instâncias para todos os objetos internos, garantindo independência entre cópia e original.

Vantagens:

  • Alterações na cópia não afetam o original.
  • Evita compartilhamento indesejado de referências.
O problema

Problemas com Cloneable

A interface Cloneable no Java foi mal projetada e é amplamente desencorajada por especialistas como Joshua Bloch e Brian Goetz, além da própria documentação oficial do Java. Principais problemas:

  • Não fornece um método clone(), tornando seu uso inconsistente.
  • super.clone() faz apenas uma cópia rasa (shallow copy), podendo causar efeitos colaterais imprevisíveis.
  • Quebra encapsulamento, pois cria objetos sem chamar o construtor.
  • Objetos internos mutáveis podem ser compartilhados indevidamente, levando a bugs difíceis de rastrear.
  • Melhores alternativas existem, como construtores de cópia e métodos de fábrica.
Quatro vozes, um consenso

O que dizem os especialistas

Os especialistas seguem uma linha consistente: evitar Cloneable e preferir alternativas mais seguras.

Joshua Bloch

Effective Java (3ª edição, 2018), Item 13

The resulting mechanism is fragile, dangerous, and extralinguistic: it creates objects without calling a constructor.

Recomenda construtores de cópia ou métodos de fábrica como alternativa mais segura.

By convention, classes that implement Cloneable should override Object.clone() with a public method.

Sem implementar Cloneable, chamar clone() lança CloneNotSupportedException: não há garantia de comportamento consistente.

A recomendação prática

Prefira um construtor de cópia a Cloneable.

Cloneable é um mecanismo falho e deve ser evitado. Os próprios criadores e arquitetos do Java recomendam não usá-lo e preferir abordagens mais seguras:

  • Construtores de cópia: garantem uma cópia controlada e previsível.
  • Métodos de fábrica (copy()): melhor prática para testes e produção.
  • MapStruct: automação eficiente para cópias profundas de objetos complexos.

Síntese

Shallow copy compartilha referências entre cópia e original → deep copy isola o estado, mas dá mais trabalho para implementar → Cloneable promete resolver isso automaticamente, mas quebra encapsulamento e não garante comportamento consistente → por isso Bloch, Goetz e a própria documentação do Java recomendam abandoná-lo em favor de construtores de cópia ou métodos de fábrica.
