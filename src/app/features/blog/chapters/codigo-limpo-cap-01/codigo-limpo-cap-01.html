Código Limpo

Resumo conceitual do Capítulo 1 de Código Limpo: Habilidades Práticas do Agile Software

O código nunca vai desaparecer. Por isso, escrevê-lo bem e mantê-lo limpo continuamente é a habilidade profissional mais fundamental de um programador.

Ponto de partida

Sempre haverá código

Martin abre rejeitando a ideia de que ferramentas de alto nível ou geração automática algum dia eliminarão a programação. Especificar requisitos com o detalhe suficiente para que uma máquina os execute é programar, e essa especificação, por mais alto nível que a linguagem se torne, continuará sendo código. Não há atalho que escape da precisão que só o código oferece.

O problema

O custo de ter um código confuso

Todo programador com alguns anos de estrada já foi retardado por código ruim (o próprio ou o alheio). Martin descreve o padrão: cada alteração passa a quebrar outras duas ou três partes do sistema; nada é trivial; a bagunça cresce até não ser mais possível arrumá-la. Conforme a confusão aumenta, a produtividade despenca em direção a zero. A reação da gerência (contratar mais gente) só acelera a queda, porque os recém-chegados não distinguem uma mudança que ajuda de uma que atrapalha.

Figura 1.1 do livro Produtividade × tempo. À medida que o código se torna mais confuso, a produtividade da equipe cai assintoticamente para perto de zero; nunca chega a zero, mas, para todos os efeitos práticos, o time trava.

O Grande Replanejamento

A equipe se rebela, a gerência cede, e nasce um time novo para reescrever tudo do zero, enquanto o sistema antigo continua precisando de manutenção. As duas equipes entram numa corrida que pode durar anos; quando o novo sistema finalmente alcança o antigo, os membros originais já foram embora e o ciclo de degradação recomeça.

Atitude

Martin recusa as desculpas de sempre: prazos curtos, requisitos que mudam, gerentes e clientes difíceis. A responsabilidade pela bagunça é nossa. Cabe ao programador, como profissional, defender o código com a mesma paixão com que gerentes defendem prazos, inclusive dizendo não quando ceder significa produzir uma zona.

Citada por Kent Beck

"Depois" é igual a nunca: a Lei de LeBlanc

Ilustrando por que código ruim se acumula, Martin lembra que todo programador já disse "eu limpo isso depois" ao ver a própria bagunça funcionando. A lei de LeBlanc nomeia o hábito: adiar a limpeza do código equivale, na prática, a nunca fazê-la.

Nota de tradução Esta edição em português (Alta Books) traz a frase como "Nunca é tarde", o que inverte o sentido do original em inglês, "Later equals never" ("depois é igual a nunca"). Vale ter isso em mente ao citar a passagem.
O dilema central

Ir rápido só é possível com código limpo

Martin descreve o dilema que todo programador enfrenta: bagunça reduz a velocidade, mas a pressão do prazo empurra para a bagunça. A resolução dele é direta: desorganização reduz a velocidade instantaneamente. A única forma de ir mais rápido, a única forma de cumprir o prazo, é manter o código limpo o tempo todo.

Seis vozes, uma pergunta

O que é um código limpo?

Sem uma definição única, Martin recorre a seis programadores influentes. Juntas, as respostas formam quase um sumário do livro inteiro.

Bjarne Stroustrup

criador do C++

Gosto do meu código elegante e eficiente. A lógica deve ser direta... o tratamento de erro completo... O código limpo faz bem apenas uma coisa.

Introduz elegância, atenção aos detalhes de erro, e a ideia de responsabilidade única.

Grady Booch

autor de OOAD with Applications

Um código limpo é simples e direto. Ele é tão bem legível quanto uma prosa bem escrita... repleto de abstrações claras.

Foco em legibilidade: código deve se ler como boa literatura.

"Big" Dave Thomas

fundador da OTI, pai do Eclipse

Um desenvolvedor pode ler e melhorar um código limpo. Ele tem testes... oferece apenas uma maneira, e não várias, de se fazer uma tarefa.

Acrescenta testes e API mínima: limpo é o que outra pessoa consegue alterar com segurança.

Michael Feathers

autor de Working Effectively with Legacy Code

Um código limpo sempre parece que foi escrito por alguém que se importava. Não há nada de óbvio no que se pode fazer para torná-lo melhor.

Resume tudo em uma palavra: cuidado (care).

Ron Jeffries

autor de Extreme Programming Installed

Regras de Beck, em ordem: passa em todos os testes; sem duplicação; expressa todas as ideias do sistema; minimiza entidades.

Foco em duplicação zero e nomes/expressividade acima de tudo.

Ward Cunningham

criador do Wiki e coautor do XP

Você sabe que está criando um código limpo quando cada rotina se mostra como o que você esperava... a linguagem foi feita para o problema.

Código limpo nunca surpreende: é previsível, quase óbvio de ler.

A conclusão prática do capítulo

Deixe a área do acampamento mais limpa do que como você a encontrou.

Emprestada dos escoteiros americanos, a Regra do Escoteiro é a resposta de Martin para "como evitar que o código degrade de novo". Não basta escrever bem uma vez: cada vez que você toca um arquivo, deixa-o um pouco melhor: renomeia uma variável, quebra uma função grande, remove uma duplicação, simplifica um if aninhado. Pequenas melhorias contínuas, feitas por todos, impedem a degradação; para o autor, é isso que separa profissionalismo de mera entrega.

Como as peças se encaixam

Síntese

O capítulo monta uma cadeia de causa e efeito: código sempre existirá → código ruim tem custo real e composto (Figura 1.1) → adiar a limpeza equivale a nunca limpar (Lei de LeBlanc) → logo, ir rápido de verdade exige manter o código limpo o tempo todo → e "limpo" significa, nas palavras de seis autores diferentes, elegante, legível, testado, sem duplicação e cuidado por alguém que se importa → o mecanismo para sustentar isso, dia após dia, é a Regra do Escoteiro. É a tese fundacional sobre a qual o resto do livro constrói suas técnicas.
