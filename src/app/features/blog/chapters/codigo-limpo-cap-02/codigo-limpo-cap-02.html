Nomes Significativos

Resumo conceitual do Capítulo 2 de Código Limpo: Habilidades Práticas do Agile Software.

Se um nome requer um comentário, então ele não revela seu propósito, e nomear bem é, sozinho, capaz de transformar código confuso em código óbvio.

Abertura

Nomeamos o tempo todo

Tim Ottinger abre o capítulo lembrando que há nomes por todos os lados em um software: variáveis, funções, parâmetros, classes, pacotes, arquivos. Como nomeamos tanto, é melhor que façamos isso bem, e o resto do capítulo é uma lista de regras simples e concretas para isso.

O exemplo que abre o capítulo

O mesmo código, três nomes depois

Ottinger mostra como um único código pode passar de ilegível a óbvio só trocando nomes, sem mudar nem a lógica, nem o número de linhas.

v1: nada revela o propósito 
public List<int[]> getThem() {{ '{' }}
    List<int[]> list1 = new ArrayList<int[]>();
    for (int[] x : theList)
        if (x[0] == 4)
            list1.add(x);
    return list1;
{{ '}' }}
nomes explicativos ↓
v2: nomes explicativos, mesma lógica 
public List<int[]> getFlaggedCells() {{ '{' }}
    List<int[]> flaggedCells = new ArrayList<int[]>();
    for (int[] cell : gameBoard)
        if (cell[STATUS_VALUE] == FLAGGED)
            flaggedCells.add(cell);
    return flaggedCells;
{{ '}' }}
classe própria em vez de vetor mágico ↓
v3: uma classe Cell substitui os números mágicos 
public List<Cell> getFlaggedCells() {{ '{' }}
    List<Cell> flaggedCells = new ArrayList<Cell>();
    for (Cell cell : gameBoard)
        if (cell.isFlagged())
            flaggedCells.add(cell);
    return flaggedCells;
{{ '}' }}

Nada na complexidade do código mudou: mesmo número de operadores, constantes e itens aninhados. O que mudou foi o quanto o código consegue responder sozinho: o que é theList? o que significa o índice 0? o que é o valor 4? Nomear bem elimina a necessidade de perguntar.

O corpo do capítulo

Dezessete regras práticas

Ottinger organiza as regras em blocos soltos ao longo do texto. Aqui elas estão agrupadas por intenção.

i.

Clareza: o nome precisa se explicar sozinho

Use nomes que revelem o propósito

O nome deve dizer por que existe, o que faz e como é usado. Se precisa de comentário, falhou.

int d; → int elapsedTimeInDays;

Evite informações erradas

Não use palavras com significado técnico específico (hp, aix) fora de contexto, nem nomes quase idênticos entre si.

accountList só se for List de verdade

Faça distinções significativas

Números ou palavras genéricas anexadas só para diferenciar (a1, a2, ProductInfo/Data) não comunicam nada.

copyChars(a1, a2) → copyChars(source, destination)

Use nomes pronunciáveis

Se não dá pra falar em voz alta sem soar bobo, a comunicação em equipe sofre: programação é atividade social.

genymdhms → generationTimestamp

Use nomes passíveis de busca

O tamanho do nome deve ser proporcional ao escopo. Constantes soltas (5, 7) são impossíveis de localizar com grep.

5 → WORK_DAYS_PER_WEEK
ii.

Disciplina: não force o leitor a decodificar

Evite codificações

Notação Húngara e prefixos de tipo eram necessários com compiladores fracos; hoje só atrapalham a leitura e a refatoração.

PhoneNumber phoneString; → PhoneNumber phone;

Evite prefixos m_ e a notação I de interface

Editores modernos já destacam campos membro; e o consumidor de uma interface não precisa saber que é uma.

IShapeFactory → ShapeFactory (+ ShapeFactoryImp)

Evite o mapeamento mental

Nomes de uma letra (fora contadores i, j, k de escopo curto) obrigam o leitor a traduzir mentalmente. Clareza é fundamental.

Nomes de classes e métodos

Classes levam substantivos (Cliente, Conta); métodos levam verbos (postarPagamento). Construtores sobrecarregados viram factories nomeados.

new Complex(23.0) → Complex.FromRealNumber(23.0)
iii.

Consistência e contexto

Não dê uma de espertinho

Piadas internas e gírias só fazem sentido para quem compartilha o humor do autor. Prefira clareza a diversão.

HolyHandGrenade → DeleteItems

Uma palavra por conceito

Escolha um termo (buscar, obter ou pegar) e mantenha-o consistente para o mesmo tipo de operação em toda a base.

Não faça trocadilhos

O oposto da regra anterior: não reaproveite a mesma palavra para dois propósitos diferentes só por "consistência" superficial.

add() só se a semântica for sempre a mesma

Domínio da solução e do problema

Use termos técnicos (AccountVisitor, JobQueue) quando fizer sentido; use o vocabulário do especialista de domínio quando não houver equivalente técnico.

Adicione contexto significativo

Variáveis soltas como number, verb e pluralModifier só fazem sentido dentro de uma classe que as agrupe.

→ classe GuessStatisticsMessage

Não adicione contexto desnecessário

Prefixar tudo com o nome do projeto (GSD) ou da aplicação atrapalha o autocompletar e não ajuda ninguém.

GSDAccountAddress → AccountAddress
Últimas palavras do capítulo

O mais difícil sobre escolher bons nomes é ter boas habilidades de descrição e um histórico cultural compartilhado.

Ottinger encerra dizendo que isso é uma questão de aprendizado, não uma habilidade técnica, gerencial ou empresarial, e que a maioria das pessoas na área não pratica o suficiente. Ele também desarma o medo mais comum: o de renomear algo e "incomodar" o time. Com ferramentas modernas de refatoração, renomear é barato; deixar um nome ruim parado é que tem custo composto, como o capítulo 1 já havia mostrado.

Como as peças se encaixam

Síntese

O capítulo prova sua tese com o próprio exemplo de abertura: o mesmo algoritmo, exatamente com a mesma complexidade, passa de opaco a autoexplicativo só pela escolha dos nomes. As 17 regras que seguem não são uma lista arbitrária: cada uma ataca uma forma específica de nome ruim (vago, enganoso, ambíguo, impronunciável, impossível de buscar, codificado, mal contextualizado). Juntas, elas devolvem ao código a característica central do Capítulo 1: ler um código limpo deve ser como ler prosa bem escrita, sem exigir do leitor nenhuma tradução mental.
